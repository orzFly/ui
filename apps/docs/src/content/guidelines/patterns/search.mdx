**A box people search from keeps the queries they ran and offers them back. `QueryBox` turns the
browser's own input history off, so a box given no `history` offers none.**

<Example of={IssueSearch} />

Search for `is:open` and then for `flaky test`, and click into the empty box: both wait there,
newest first. Type `fl` and the one it begins rises above the submit row; type `test` and the one
it only appears in waits below it. Tab loads a past query to keep editing; Enter or a click runs
it again.

## An empty box

The submit row stays when the box is empty, and `renderSubmitRow` gets `""`. Choosing it submits
the empty query, so draw the row as the place an empty query goes: every issue, all mail, or a
search page that explains the syntax. Enter with no row picked still submits nothing.

## Which boxes keep a history

Give `history` to a box a reader comes back to search from: the search in an app's header, the
query over a list of issues or mail. Keep it from a query-typed field in a form, such as the
filter rule on [Forms](/guidelines/patterns/forms/): that field holds one value the form saves,
and a history there would offer other rules' queries as if they were this one's.

## Where the queries are kept

`useQueryHistory` keeps them in the browser, under a `storageKey` named after the app, and after
the person signed in where several share one browser. Inside the key, each `scope` is a bucket of
its own. Pick the scope from whatever a query's meaning depends on: a label of one project finds
nothing in another, so each project gets its own. A box whose queries mean the same everywhere
names its one bucket.

## When a query counts as searched

The box records nothing. Call `record` in `onSubmit`, where the app runs the search, and nowhere
else:

- A query that names one thing and goes straight to it, an issue's number say, is a jump, not a
  search. Do not record it. Only Enter in the box with the panel showing and no row highlighted,
  `{ from: "input", panelOpen: true }`, may jump.
- The submit row asks for a search of exactly what was typed, and so does Enter after Escape hid
  the panel (`panelOpen: false`). Search them as they are, even when they name one thing.
- A submission the app refuses, a form field that fails its check, is not a search either.
- A past query chosen from its row arrives `from: "history"`. It was a search when it was
  recorded, so search it as it is, without asking again whether it names one thing.

Record a query that ran, whichever way it came; it moves back to the top.

## Waiting on a query

Sometimes `onSubmit` cannot tell at once where a query goes: a pasted reference has to be looked
up before the app knows whether it names one thing. Set `busy` until it knows. The box marks its
input busy for a screen reader and draws nothing, because the wait is usually shorter than the
half second under which [Loading](/guidelines/patterns/loading-empty-and-error/) adds nothing new.

## Linking the results

When the results have an address, give `queryHref`: each past query becomes a link to them, so a
middle click or a modified click opens them in a new tab, as any place does on
[Navigation](/guidelines/patterns/navigation/). A plain click still goes through `onSubmit`.

## Forgetting a query

Each past query carries an × that forgets it: on the highlighted row under a mouse, and on every
row on a touch screen, where nothing is hovered. Shift+Delete forgets the highlighted one from the
keyboard, as in a browser's address bar.

Forgetting asks nothing and offers no Undo. What goes is a query, which can be searched again,
and the row goes from under the finger that tapped its ×, so nothing vanishes unseen
([Destructive actions](/guidelines/patterns/destructive-actions/)).

## Drawing values

Draw a value in the panel as the app draws it everywhere else, so it is known at a glance: a label
as its chip, a status as its pill, a person with their avatar. Put what each is drawn from on the
provider's options (a label's colour, a person's login) and draw it in `renderValue`. A mark such
as an avatar takes the icon's place and leaves the words where every row's words start; a chip
takes the value's text; the hint still follows. Keep the value's name in the row either way: it is
what a screen reader reads and what the reader matched by typing.

Type `label:` or `assignee:` in the example at the top. The schema already offers `@me`; the
member search restates it with who that is, and the box keeps one `@me`, where it stood, now with
an avatar.

## Words the app finishes

Some words only the app can finish: a project's prefix, which an issue's number follows, means
nothing to the schema. Offer them from a `RowSource` that `completes`, with an `apply` that writes
the word into the query and puts the caret after it. Its rows then behave as the schema's own
completions: Enter, a click or Tab rewrites the query and keeps the reader in the box, and nothing
is searched. A row that goes somewhere, a jump to one issue, stays in a source without
`completes`, so choosing it submits.
